# Telegram: подключение и границы работы

EduSafe использует Supabase Edge Functions для Telegram. Постоянно работающий процесс Python/aiogram на Vercel не требуется: Telegram отправляет входящие обновления на HTTPS webhook, а отдельный обработчик читает надёжную очередь уведомлений из PostgreSQL.

## Состояние по умолчанию

- У организации выбран режим `mock`.
- Учебные тревоги всегда обрабатываются как демонстрационные, даже если у организации включён Telegram.
- Для настоящей отправки нужны одновременно `notification_mode = telegram`, секрет бота и `TELEGRAM_DELIVERY_ENABLED=true`.
- Без подключения бота веб-приложение продолжает работать. Записи, подтверждения преподавателя и тревоги сохраняются в базе независимо от внешней доставки.
- `sent` означает, что Telegram API вернул успешный результат и номер сообщения. Это не подтверждение прочтения или прибытия помощи.

Тесты в репозитории используют подставной HTTP-транспорт. Они не отправляют сообщения в Telegram и не доказывают, что конкретный рабочий бот настроен.

## Edge Functions

| Функция | Назначение | Защита |
| --- | --- | --- |
| `notification-worker` | Проверка отложенных правил и отправка сообщений из очереди | Заголовок `x-edusafe-worker-secret`, проверяемый через служебную RPC |
| `telegram-webhook` | Подключение аккаунта по одноразовой ссылке и принятие тревоги сотрудником | Заголовок Telegram `x-telegram-bot-api-secret-token` |

Для этих двух функций применяется `verify_jwt=false`: Telegram не отправляет Supabase JWT, а планировщик использует отдельный ограниченный секрет. Это не делает обработчики публично доступными без авторизации — они отклоняют запрос до выполнения действий, если собственная проверка секрета не пройдена.

Добавьте соответствующие секции в `supabase/config.toml`:

```toml
[functions.notification-worker]
verify_jwt = false

[functions.telegram-webhook]
verify_jwt = false
```

## Секреты и настройки

| Значение | Где используется | Примечание |
| --- | --- | --- |
| `SUPABASE_URL` | Обе функции | Предоставляется средой Supabase |
| `SUPABASE_SERVICE_ROLE_KEY` либо карта `SUPABASE_SECRET_KEYS` | Обе функции | Только серверная среда; не переносить в `NEXT_PUBLIC_*` |
| `TELEGRAM_BOT_TOKEN` | Обе функции | Токен бота, предоставленный владельцем через настройки секретов |
| `TELEGRAM_DELIVERY_ENABLED` | Обе функции | Настоящие отправки разрешены только при точном значении `true` |
| `TELEGRAM_WEBHOOK_SECRET` | Webhook | Необязательная альтернатива хешу секрета в БД |
| `APP_BASE_URL` | Webhook | HTTPS-адрес развёрнутого EduSafe для кнопки перехода в кабинет |

Секрет worker проверяется служебной функцией `edusafe_authorize_worker`. Его хеш устанавливается с помощью `edusafe_set_integration_secret` с именем `worker`. Секрет webhook аналогично можно установить под именем `telegram_webhook`; если задан `TELEGRAM_WEBHOOK_SECRET` в окружении, webhook проверяет его вместо значения в БД.

Используйте независимые случайные секреты длиной не менее 32 символов из набора `A–Z`, `a–z`, `0–9`, `_`, `-`. Не используйте токен самого бота как секрет webhook или worker. Не сохраняйте значения в Git, README, скриншотах и логах.

## Порядок реального подключения

1. Владелец создаёт или выбирает бота через BotFather и сохраняет его токен в секретах Supabase Edge Functions.
2. Создаются независимые секреты worker и webhook. В БД сохраняются их хеши через служебные RPC. Для cron значение worker помещается в Supabase Vault.
3. Развёртываются обе функции вместе с файлами `supabase/functions/_shared/`.
4. Устанавливаются `APP_BASE_URL` и, после разрешения владельца на реальные сообщения, `TELEGRAM_DELIVERY_ENABLED=true`.
5. Методом Telegram `setWebhook` регистрируется HTTPS-адрес `/functions/v1/telegram-webhook` с полем `secret_token`, совпадающим с настроенным секретом. Разрешённые типы обновлений — `message` и `callback_query`.
6. Результат регистрации проверяется через `getWebhookInfo`, включая URL и последнюю ошибку. Удалять ожидающие обновления при обычном обновлении кода не нужно.
7. В своём защищённом веб-кабинете пользователь создаёт одноразовый код подключения и открывает ссылку `https://t.me/<имя_бота>?start=<код>`. Имя бота берётся из реально настроенного бота.
8. Только после проверки своего подключения администратор включает режим Telegram для организации и выполняет согласованный тест на тестовом получателе.

Регистрация webhook и реальные сообщения не выполняются автоматически при обычном запуске сайта.

## Подключение пользователя

Обработчик `/start <код>` принимает код только из личного диалога. Идентификатор пользователя определяется из обновления Telegram, а не из введённого им `user_id`.

Проверяется срок кода, его область действия и связанная веб-учётная запись. Повтор того же обновления не должен создавать другую связь. Повтор уже использованного кода допустим только для той же связанной Telegram-идентичности — это нужно для безопасного восстановления после потери ответа.

Связь с Telegram сама по себе не выдаёт доступа к ребёнку. Такой доступ определяется активной проверенной связью представителя с учеником в EduSafe.

Код не повторяется в ответном сообщении и не записывается в журналы функций.

## Команды

| Команда | Поведение первой версии |
| --- | --- |
| `/start` | Инструкция по подключению |
| `/start <код>` | Подключение Telegram к существующему веб-аккаунту |
| `/help` | Справка и переход в защищённый кабинет |
| `/today`, `/children`, `/absence` | Переход в веб-кабинет для посещаемости, детей и причин отсутствия |
| `/language` | Подсказка о настройках в кабинете |

Ответы служебных команд доступны на русском и казахском; исходный язык выбирается по `language_code` отправителя. Данные о детях эти команды не раскрывают в групповом чате.

Подробные действия родителя выполняются в веб-приложении. Бот не изображает несуществующие нативные формы посещаемости или подачи заявлений.

## Подтверждение тревоги

Настоящее уведомление о тревоге может содержать кнопку «Принял / Қабылдадым». В callback передаётся только UUID инцидента. Обработчик получает Telegram ID нажавшего пользователя и заново проверяет его связь с учётной записью, организацию и роль.

Нажатие кнопки посторонним пользователем не принимает тревогу. Повторное принятие не создаёт второй инцидент. Закрытие и пояснение результата выполняются в веб-приложении.

## Доставка и ошибки

- Записи отправки захватываются с арендой и уникальным `lease_token`.
- Перед отправкой повторно проверяются актуальность события и право получателя видеть его.
- Работает одна арендованная отправляющая задача; внутри неё есть ограничение частоты и пауза между сообщениями одному пользователю.
- При `429` используется `retry_after`; оставшаяся часть текущей партии откладывается.
- Сетевой таймаут считается неопределённым исходом, а не успешной доставкой.
- Постоянные ошибки, включая блокировку бота, видны в журнале уведомлений.
- Доставка внешнему сервису допускает редкий повтор после сбоя между принятием сообщения Telegram и сохранением результата в БД. Номер события помогает сопоставить повторы.

Telegram и браузер не являются гарантированным каналом экстренного реагирования. Организация заранее задаёт резервный способ связи, который виден в приложении при проблеме с передачей.
