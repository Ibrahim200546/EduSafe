# Эксплуатация уведомлений и фоновых правил

## Разделение процессов

Vercel обслуживает веб-приложение. Supabase хранит данные, применяет права доступа, проверяет запланированные события и запускает короткие Edge Functions. Открытый браузер преподавателя не является планировщиком системы.

В PostgreSQL в одной транзакции сохраняются изменение предметных данных и связанные задания уведомлений. Отдельный обработчик отправляет их после фиксации транзакции. Это позволяет восстановить обработку после перезапуска без потери исходного инцидента или записи посещения.

## Планировщик

Служебная RPC `edusafe_process_due()` проверяет актуальные занятия и эскалации. Её может вызывать `pg_cron`; обработчик `notification-worker` также вызывает её перед чтением очереди. Повторный запуск не должен создавать повторное логическое уведомление.

Для автоматической внешней отправки необходим отдельный запуск Edge Function по расписанию. Наличие только SQL-задачи проверки посещаемости не означает, что отправляющий worker подключён.

Пример команды для `pg_cron`, которая вызывает worker через `pg_net`:

```sql
select cron.schedule(
  'edusafe-notification-worker',
  '* * * * *',
  $cron$
  select net.http_post(
    url := 'https://<PROJECT_REF>.supabase.co/functions/v1/notification-worker',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'x-edusafe-worker-secret', (
        select decrypted_secret
        from vault.decrypted_secrets
        where name = 'edusafe_worker_secret'
        limit 1
      )
    ),
    body := '{}'::jsonb,
    timeout_milliseconds := 60000
  )
  where exists (
    select 1 from vault.decrypted_secrets
    where name = 'edusafe_worker_secret'
  );
  $cron$
);
```

Это шаблон настройки: замените `<PROJECT_REF>` реальным идентификатором проекта. Сначала должны быть развёрнуты функция и её секреты. Значение в Vault должно совпадать с секретом, хеш которого зарегистрирован для имени `worker` через `edusafe_set_integration_secret`.

Расписание SQL-проверок и расписание внешней отправки проверяются отдельно. Для существующего задания используйте его обновление, а не создавайте дополнительные копии с другими именами.

Минутное расписание даёт соответствующую задержку запуска. Нельзя обещать мгновенное Telegram-оповещение или точное время реакции сотрудника. Веб-панель инцидентов получает состояние из базы отдельно от Telegram.

## Ограничения одной партии

Текущий worker захватывает до восьми заданий, приоритетных по серверной очереди, и ограничивает время обработки партии. Оставшиеся задания сохраняются для следующего запуска. При большом потоке нужно измерить задержку очереди и обоснованно настроить размер партии и расписание.

Глобальная аренда worker не позволяет одновременно обрабатывать очередь двумя запусками. Завершение каждой записи требует соответствующего `lease_token`: завершившийся поздно старый обработчик не должен перезаписать результат новой аренды.

Внешний HTTP-запрос выполняется без длительно открытой транзакции БД. Если процесс завершится после принятия сообщения Telegram, но до сохранения результата, возможна повторная доставка. Это ограничение внешнего канала отражено в номере события и документации.

## Состояния уведомлений

| Состояние | Что известно |
| --- | --- |
| `queued` | Задание ожидает первой или повторной попытки |
| `processing` | Задание временно захвачено worker |
| `mock` | Обработка выполнена в демонстрационном режиме, внешнего сообщения нет |
| `sent` | Telegram API принял сообщение и вернул его номер |
| `failed` | Отправка завершилась ошибкой, требующей внимания |
| `suppressed` | Событие или право получателя изменились; отправка более не нужна |

Завершение отправки и принятие тревоги сотрудником — разные записи. Уведомление `sent` не меняет само по себе статус тревоги на `acknowledged`.

## Типовые неисправности

| Признак | Что проверить |
| --- | --- |
| HTTP 401 у worker | Наличие собственного заголовка и соответствие хеша секрета |
| HTTP 503 `service_not_configured` | Серверные переменные окружения Supabase |
| HTTP 503 `authorization_unavailable` | Доступность БД, наличие миграций и служебных RPC |
| HTTP 202 `busy` | Уже действующую аренду worker; повторный параллельный запуск не нужен |
| `telegram_delivery_disabled` | Явное включение доставки в окружении функций |
| `telegram_not_configured` | Наличие токена бота в секретах Edge Functions |
| `telegram_not_linked` | Подключение получателем своего Telegram-аккаунта |
| `telegram_rate_limited` | Время следующей попытки; worker учитывает `retry_after` |
| `telegram_403` | Получатель мог заблокировать бота; успешная доставка не заявляется |
| Долго остаётся `processing` | Истечение аренды и последующий запуск worker |
| Уведомлений нет в выходной | Возможно, ожидаемое поведение календаря; проверить конкретное занятие |
| Журнал обновлён, но старое сообщение не отправлено | Проверить `suppressed`: данные могли стать неактуальными |

После исправления постоянной ошибки повторные отправки разрешайте контролируемо: сначала перепроверьте получателя и актуальность события. Не помечайте задания `sent` вручную.

## Наблюдаемость

Проверяйте:

- время последнего успешного запуска планировщика;
- возраст самого старого актуального задания;
- количество `failed` и зависших `processing`;
- ошибки Edge Functions;
- не принятые сотрудниками тревоги;
- повторяющиеся ошибки календаря и назначений;
- доступность базы и работоспособность резервного способа связи.

Логи функций содержат тип события, идентификатор запуска и счётчики. Токены, коды приглашений, тексты детских уведомлений и секреты в них не записываются.

## Проверки обработчиков

Из корня проекта на Node.js 24 (на этой версии выполнены проверки обработчиков):

```text
node --experimental-strip-types --test supabase/functions/_shared/worker.test.ts
```

Проверка типов в Deno:

```text
deno check --config supabase/functions/deno.json supabase/functions/notification-worker/index.ts supabase/functions/telegram-webhook/index.ts
```

Набор тестов проверяет запрет запросов без секрета, режимы mock и учебных тревог, отзыв доступа, неопределённый исход отправки, `429`, постоянную ошибку, арендованный worker, дедупликацию webhook, запрет привязки в группах и идентичность сотрудника при принятии тревоги.

Эти проверки выполняются с подставными HTTP и RPC. Дополнительно нужны интеграционные SQL-тесты, проверка развёрнутых функций и согласованный тест реального бота. В отчёте поставки следует указывать, какие из этих этапов фактически выполнены.

## Восстановление

Резервная копия должна охватывать схему, предметные данные, связи представителей, историю инцидентов и очередь. Auth и серверные секреты учитываются отдельно по выбранному процессу резервного копирования Supabase.

Восстановление проверяется в отдельной тестовой базе. После восстановления реальные уведомления сначала оставляют выключенными; затем проверяют, что старые события не породят неактуальную массовую рассылку.

Наличие резервной копии без проверки восстановления не считается проверенным сценарием восстановления.
