# База данных EduSafe

## Устройство

Рабочие данные хранятся в PostgreSQL проекта Supabase. Supabase Auth выдаёт сессии; организационные роли и назначения хранятся в `memberships`, а связи представителей — в `guardian_links`. `user_metadata` используется исключительно для отображаемого имени нового пользователя и не предоставляет полномочий.

Миграции применяются по порядку:

1. `202611030001_schema.sql` — таблицы, внешние ключи, уникальные ограничения, индексы, включение RLS.
2. `202611030002_authorization.sql` — актуальные проверки сессии и ролей, политики чтения, снимок рабочей области.
3. `202611030003_domain_helpers.sql` — журналирование, transactional outbox и вымышленные данные.
4. `202611030004_actions.sql` — транзакционные операции приложения.
5. `202611030005_worker.sql` — захват фоновых задач, повторная проверка отправки, Telegram-связи, эскалация и SQL-расписание.
6. `202611030006_foreign_key_indexes.sql` — индексы внешних ключей, операций отзыва и выборок в пределах организации.

Схема `app_private` не должна включаться в список схем, доступных через Supabase Data API. На всех таблицах в `public`, а также на внутренних таблицах, включена RLS. Анонимный пользователь не получает доступ к таблицам или пользовательским RPC.

### Осознанно закрытые внутренние таблицы

Supabase Security Advisor может показывать информационное сообщение `RLS Enabled No Policy` для семи таблиц в `app_private`: `integration_secrets`, `invitations`, `qr_challenges`, `telegram_link_tokens`, `telegram_links`, `telegram_updates`, `worker_lease`.

Для этих таблиц отсутствие пользовательских политик намеренно: обычные роли не должны читать или изменять их строки. Дополнительно отозваны табличные привилегии `PUBLIC`, `anon` и `authenticated`; схема не выставляется в Data API. Проверенные операции выполняют строго ограниченные внутренние функции либо служебная роль. Добавление разрешающей политики `USING (true)` ради удаления такого сообщения открыло бы ненужный путь доступа и не требуется.

Описание диагностического сообщения: [Supabase Database Linter — RLS Enabled No Policy](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

### Индексы и информационные предупреждения

Проверка первых пяти миграций выявила 25 внешних ключей без полного покрывающего индекса. Миграция 006 добавляет 24 индекса: индекс приглашений `(school_id, student_id)` покрывает два внешних ключа. Остальные покрывают ссылки на авторов и ответственных, пары «организация — занятие/помещение/инцидент», операции отмены сообщений и отзыва доступа представителя. Индекс `telegram_link_tokens(user_id, expires_at)` также обслуживает фактическую операцию погашения предыдущих токенов пользователя.

Существующие индексы по глобальному идентификатору записи и времени сохраняются: они обслуживают упорядоченную историю конкретной записи. Новые индексы с ведущим `school_id` дополнительно покрывают выборки и обслуживание данных в пределах организации. Изменения прав доступа или предметной логики миграция 006 не содержит.

Сообщение `Unused Index` на новой базе означает отсутствие наблюдавшихся обращений за доступный период статистики. Само по себе оно не является основанием удалять индекс. Решение об удалении принимается по достаточно длительной статистике реальной нагрузки, планам `EXPLAIN` и стоимости записи. Индексы на уже большой рабочей базе следует создавать в согласованное время либо отдельными командами `CREATE INDEX CONCURRENTLY`; начальная миграция использует обычный `CREATE INDEX`.

Описания диагностик: [внешние ключи без индекса](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys), [неиспользованные индексы](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index). Ускорение в конкретное число раз не заявляется: сравнительный нагрузочный замер для индексов не проводился.

## Границы доступа

`authenticated` имеет право читать только строки, разрешённые RLS. Прямые `INSERT`, `UPDATE`, `DELETE` для этой роли запрещены, в том числе для администратора школы. Изменения проходят через `edusafe_action` и повторно проверяют полномочия на сервере БД.

Публичные RPC являются `SECURITY INVOKER`-обёртками. Привилегированные реализации находятся в `app_private`, имеют фиксированный пустой `search_path`, полностью квалифицированные имена таблиц и явно ограниченный `EXECUTE`. У внутренних служебных функций нет разрешения `EXECUTE` для обычного пользователя.

Каждый пользовательский путь проверяет:

- существование `auth.uid()`;
- наличие подписанного `session_id` в JWT;
- существование соответствующей строки в `auth.sessions` с тем же владельцем;
- срок `not_after`, если он задан;
- отсутствие блокировки и удаления пользователя;
- актуальные назначения в организации.

Поэтому удалённая сервером сессия перестаёт открывать данные БД, даже если старый access token ещё не достиг `exp`. Telegram — отдельная связанная идентичность: служебный webhook проверяет секрет запроса, связь Telegram ID, активность пользователя и свежие роли. Выход из веб-сессии сам по себе не отключает ранее подключённого Telegram-бота; для этого предусмотрено отдельное действие `disconnect_telegram`.

Преподаватель получает доступ по действующим `group_ids`; старое поле `teacher_id` в историческом уроке не сохраняет доступ после снятия назначения. Охране доступны её сигналы и помещения, без академического списка учеников. Родитель видит только активные подтверждённые связи. Для совершеннолетнего студента дополнительно требуется `adult_authorized`.

Составные внешние ключи связывают организацию и объект: запись посещения не может ссылаться на ученика или занятие другой школы. Массив групп преподавателя валидируется при создании приглашения. Секреты приглашений, QR и подключения Telegram сохраняются только в виде SHA-256-хешей от случайных 192-битных токенов.

## Пользовательские RPC

### `edusafe_workspace(p_school_id uuid default null)`

Возвращает JSON согласно `src/lib/types.ts`. До подключения организации возвращает `school: null`, собственный профиль и пустые списки. Явно запрошенная организация требует действующего членства. Без параметра выбирается первое активное назначение пользователя.

Посещения и занятия в снимке ограничены последними 31 сутками и будущим расписанием. Журнал уведомлений содержит до 200 последних доступных записей; аудит — до 150. Исторические записи продолжают храниться в БД, даже если не включены в текущую панель.

### `edusafe_action(p_action text, p_payload jsonb)`

Поддерживает операции из `IMPLEMENTATION_CONTRACT.md`, а также:

- `incident_status` с исходным `idempotency_key` — проверка неопределённого исхода нажатия;
- `disconnect_telegram` — отключение собственного канала;
- `set_member_active` — административное включение или отключение конкретной роли пользователя;
- `record_attendance.expected_versions` — необязательная карта `{student_id: version}` для отклонения устаревших изменений;
- `approve_guardian.adult_authorized` — явное разрешение связи с совершеннолетним студентом.

Ошибки прав возвращают SQLSTATE `42501`, конфликт версии — `40001`; ошибки предметной области используют сообщения `QR_INVALID`, `QR_EXPIRED`, `CHECKIN_WINDOW_CLOSED`, `INVALID_INVITATION`, `NO_MEMBERSHIP`, `NOT_FOUND` либо понятный русский текст.

Обработчики должны показывать безопасное сообщение, а не полный SQL или внутренние сведения об инфраструктуре.

## Посещаемость

`check_ins` содержит самостоятельные заявления ученика. `attendance` — итоговый статус по конкретному занятию. QR не переводит `unconfirmed` в `present` и не перезаписывает решение преподавателя. Отметка преподавателя сохраняет источник, время и версию, а предыдущий статус попадает в `attendance_changes` и аудит.

Уникальность `(school_id, lesson_id, student_id)` защищает от повторных запросов и сканирования следующего QR того же урока. Общий код действует для нескольких учеников; его использование одним человеком не погашает код для остальных.

Окно сканирования начинается за 15 минут до занятия и заканчивается в его конце. Отдельный код живёт не более 60 секунд. Время проверяется на стороне БД. Пересылка актуального кода остаётся возможной, поэтому вывод о физическом присутствии делает преподаватель.

`enrollments` сохраняет интервалы зачисления. Изменение группы завершает старый интервал и открывает новый. Отмена занятия сохраняет исторические записи и прекращает связанные отложенные уведомления.

Заявка об отсутствии с указанным занятием после одобрения переводит его запись в `excused`. Заявка без занятия относится к локальному дню её создания для подавления автоматического предупреждения; она не объявляет все произвольные будущие занятия уважительно пропущенными.

## Фоновые задачи и уведомления

Создание предметного события и строки `notifications` выполняется одной транзакцией. В mock-режиме строка получает состояние `mock`: это явно обозначенный демонстрационный приёмник, без внешней отправки. Любая учебная тревога также направляется в mock-приёмник независимо от общей настройки канала.

SQL-задача `edusafe-attendance-and-escalation` запускает `app_private.process_due(null)` раз в минуту через `pg_cron`, если расширение доступно. Необходима отдельная настройка запуска Edge worker для внешней доставки; она описана в документации worker.

Проверка посещаемости:

- рассматривает первое актуальное занятие ученика за локальный день;
- учитывает интервал зачисления, отмены, согласованные причины и период ожидания;
- не меняет статус ученика на `absent`;
- сначала проверяет готовность электронного журнала;
- при неактивированном журнале предупреждает сотрудников, а не массово сообщает родителям об отсутствии;
- повторно вызванная задача не создаёт второй экземпляр того же логического уведомления.

В сообщении сохраняется снимок времени начала занятия. Изменение расписания делает прежнее ожидающее сообщение неактуальным; ключ нового предупреждения содержит новое время занятия. Перед отправкой повторно проверяются текущий статус, срок ожидания, расписание, право получателя и связь с ребёнком.

### Служебные RPC

Доступны только `service_role`:

- `edusafe_process_due()`;
- `edusafe_claim_notifications(p_limit)`;
- `edusafe_revalidate_notification(p_id,p_lease_token)`;
- `edusafe_finish_notification(p_id,p_status,p_error,p_message_id,p_retry_after,p_lease_token)`;
- `edusafe_acquire_worker(p_run_id,p_seconds)` / `edusafe_release_worker(p_run_id)`;
- `edusafe_set_integration_secret(p_name,p_secret)`;
- `edusafe_authorize_worker(p_secret)` / `edusafe_authorize_telegram(p_secret)`;
- `edusafe_telegram_link(...)` / `edusafe_telegram_ack(...)`;
- `edusafe_claim_telegram_update(...)` / `edusafe_finish_telegram_update(...)`.

Сообщения захватываются через `FOR UPDATE SKIP LOCKED`, получают случайный `lease_token` и двухминутную аренду. Устаревший обработчик не может завершить новую аренду. После восьми неуспешных захватов задача переходит в `failed`. Повторы ограничены, а задержка учитывает `retry_after`.

Глобальная аренда диспетчера предотвращает одновременную работу нескольких внешних отправителей. Входящие Telegram updates также дедуплицируются с арендой. Повтор полностью обработанного update отличается от параллельного ещё не завершённого запроса.

Абсолютная однократность внешнего сообщения не гарантируется: канал мог принять запрос перед обрывом соединения. Номер события позволяет распознать повтор. Статус `sent` означает принятие API, а подтверждение человека фиксируется отдельно.

## Демонстрационные данные

`seed_demo` доступен администратору собственной пустой организации. Он создаёт три группы, 60 вымышленных учеников, пять дней журналов, текущие и следующие занятия, закрытую учебную тревогу и собственное системное уведомление. Учётные записи вымышленных детей или реальные получатели не создаются.

Для реальной регистрации ученика и представителя используйте ограниченное приглашение. Принятие представителем создаёт ожидающую связь; сотрудник должен подтвердить её до открытия данных.

## Проверки

`tests/database_integration.sql` предназначен для PostgreSQL/Supabase после применения миграций. Запуск требует SQL-администратора, поскольку тесты создают вымышленные `auth.users` и `auth.sessions`, затем переключаются на реальные роли `authenticated` и `service_role`.

Весь сценарий заключён в `BEGIN … ROLLBACK`. Он не отправляет сообщения, не вызывает внешние HTTP endpoints и не оставляет тестовые учётные записи. Любая неуспешная проверка прерывает транзакцию. Последний SELECT перед ROLLBACK показывает количество успешных утверждений и их названия.

Проверяются изоляция школ, запрет прямых записей, полномочия родителей и охраны, отзыв назначений, общая QR-сессия для 20 учеников, идемпотентность, источник подтверждения, конфликт версии, тревоги, восстановление результата, уникальность уведомлений, аренды, webhook-дедупликация, отзыв связи, блокировка пользователя и отзыв веб-сессии.

Разбор синтаксиса SQL/PLpgSQL является отдельной предварительной проверкой. Его успешность не заменяет выполнение интеграционного сценария на PostgreSQL. Фактические результаты запуска должны фиксироваться в итоговом отчёте проекта.

## Эксплуатационные границы

Логическая изоляция реализована в БД; браузерный деморежим использует собственные вымышленные данные и не получает привилегии в рабочей организации. Рабочая настройка Telegram требует отдельного секрета и явного включения доставки. Удаление исторических учебных записей не автоматизировано: срок хранения, экспорт и согласованный порядок удаления определяет организация перед использованием реальных данных. Журналы защищены от изменения обычными пользователями, но не являются криптографически неизменяемыми для владельца БД.
